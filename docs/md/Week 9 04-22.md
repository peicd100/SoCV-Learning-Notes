## Various Learning Techniques

這週我把焦點從「SAT solver 會學 clause」往前推了一層，開始問 learned clause 到底可以怎麼學。前一週我已經知道 CDCL 會在 conflict 發生後做 conflict analysis，然後把造成衝突的組合整理成新的 clause。可是只知道「會學」還不夠，真正影響 solver 效率的是學到的 clause 夠不夠精準、能不能形成 asserting clause、以及 backtrack 的位置是不是有意義。

我現在會用 implication graph 來理解 learning。每一次 decision 和 BCP 都會把目前 trail 串成一張因果圖，conflict 則是在這張圖最後撞到矛盾。若我只把整條 conflict path 都塞進 learned clause，雖然邏輯上可能正確，但 clause 可能太長，也可能回跳效果不好。比較好的做法是找到一個能切開 current decision level 的 cut，讓 learned clause 同時保留衝突原因，又能在回跳後立刻推出一個 literal。

這也是我覺得 1st UIP 很漂亮的地方。UIP 是 current decision level 中所有通往 conflict 的路徑都會經過的點，而 1st UIP 是最靠近 conflict 的那個點。從這裡切出 learned clause，通常可以得到比較短、比較局部、也比較有用的 clause。它不是單純記住「這次錯了」，而是記住「只要前面那些條件同時出現，就必須避免這個方向」。

做完 GV 的 stats 指令後，我對 learning 的感覺更具體了。像 `dimacs_unsat.txt` 這種小例子，最後只有 `5` 次 conflicts 和 `3` 條 learnt clauses，但 solver 就已經能證明 UNSAT。這代表每一條學到的 clause 都不是裝飾，它們直接改變後面的搜尋空間。若沒有 learning，solver 可能還要反覆走到類似的局部矛盾才知道那條路不行。

我的 insight 是，learning technique 的核心不是「多記一點東西」，而是「記剛好能讓未來 propagation 變強的東西」。如果學到的 clause 太弱，它剪不掉多少搜尋；如果學到的 clause 太多、太長，BCP 又會變慢。這讓我第一次把 conflict analysis、BCP 和 database size 看成同一個 tradeoff，而不是三個分開的主題。

## Proof Database Simplification

Proof database simplification 讓我看到 CDCL solver 另一個很工程化的面向：solver 不只要會學，也要會忘。剛開始我直覺以為 learned clause 越多越好，因為每一條 learned clause 都是原 CNF 的 logical consequence，保留下來應該只會讓搜尋更強。但讀完這段之後，我覺得這個想法太天真了。

原因是 BCP 的成本和 clause database 的大小直接相關。每次 solver 做 propagation，都要依賴 watched literals 去檢查哪些 clause 變成 unit 或 conflict。Learned clauses 若無限制累積，理論上 constraints 變強，實作上卻可能讓每一步 propagation 變慢。最後 solver 不是被 search tree 本身拖垮，而是被自己學到的大量 clause 拖慢。

所以 proof database simplification 的目標不是刪掉「錯誤」的 clause，而是在邏輯正確的前提下刪掉短期內可能幫助不大的 clause。MiniSat 裡的 `reduceDB()` 就很直接地體現這個想法：它會保留正在作為 reason 的 locked clauses，然後依照 activity 與 clause size 選擇刪除一部分 learnt clauses。這種設計讓我看到 solver 其實一直在維持一個動態工作集。

我覺得這裡最關鍵的判斷是：一條 learned clause 的價值不是固定的。它剛被學到時可能很重要，因為它對應某個剛發生的 conflict；但搜尋區域改變後，它可能很久都不再被用到。Activity heuristic 就是在近似回答這個問題：最近常參與 conflict 或 propagation 的資訊，比長期沒有被碰到的資訊更值得留下。

外部資料也讓我更確定這不是單一實作細節。Learned clause database management 本身就是 CDCL solver 的研究問題，有些研究會比較短 clause、隨機刪除、LBD 類指標或其他 reduction policy。這讓我意識到，proof database simplification 不是「把資料庫清一清」這麼簡單，而是在 memory、propagation speed、future pruning power 之間做取捨。

我現在會把 CDCL 想成一個有記憶但也有清理機制的搜尋器。Learning 讓它不再重犯同樣錯誤，simplification 則避免它被過去累積的資訊綁住。這兩者缺一個都不完整：只會學不會刪會變慢，只會刪不會保留又失去 CDCL 的優勢。

## [LN] Study miniSat Codes

### MiniSat is a classic, well-designed SAT solver implementation.

我這次先從 GV 裡的 MiniSat code structure 讀起，而不是一開始就改演算法。GV 把 SAT manager 放在 `gv/src/sat/`，真正的 MiniSat solver 則在 `gv/satsolvers/minisat/`。這個切法讓我很快看出兩層角色：`SatSolverMgr` / `MinisatMgr` 是 GV 對 solver 的包裝層，`SolverV` 才是 CDCL 搜尋、clause database、activity、trail 和 model 的核心。

最上層的 command 入口在 `gv/src/sat/satCmd.cpp`。原本只有一個 `SATSolve DIMACS` 指令，它負責接收 `-File` 參數，建立 `MinisatMgr`，再呼叫 `solve_dimacs_cnf()`。實際讀 DIMACS、建立 variables、加入 clauses、呼叫 `_solver_dimacs->solve()` 的地方則在 `gv/src/sat/minisatMgr.cpp`。這樣一層一層讀下來，我比較不會被整個 solver 嚇到，因為我知道每個檔案的責任邊界。

`SolverV` 裡最值得看的 public 狀態是 `model`、`stats`、`nVars()`、`nClauses()`、`nLearnts()`。這些資料對外部實驗很有用，而且不會破壞 solver invariant。相反地，`trail`、`watches`、`reason`、`level`、`clauses`、`learnts` 這些欄位雖然很吸引人，但它們是 solver 內部維持正確性的核心資料結構，我不應該為了做一個簡單 command 就直接暴露或改動它們。

這次閱讀讓我對 MiniSat 的「小」有新的理解。它不是功能少，而是分層很乾淨。像 `newClause()` 處理 clause 加入與 watch 設定，`propagate()` 做 BCP，`analyze()` 產生 learned clause 與 backtrack level，`search()` 把 decision、propagation、conflict handling 串成主迴圈。每個函式都很短，但合起來就是完整 CDCL solver。

### Use the algorithms from the lecture notes as a reference

我把投影片中的 modern SAT algorithm 對回 `SolverV::search()`，發現對應關係其實很清楚。主迴圈一開始先做 `propagate()`，若回傳 conflict clause，就進入 `analyze()`，產生 `learnt_clause` 和 `backtrack_level`。接著 solver 會 `cancelUntil(backtrack_level)`，再把 learned clause `record()` 進 database。這正好對應 pseudo code 裡的 BCP、conflictAnalysis、add clause 和 backtrack。

Decision ordering 則藏在 `pickBranchLit()` 和 `VarOrder::select()` 裡。`VarOrder` 不是用一個普通 list 找下一個 variable，而是用 heap 搭配 activity，讓最近被 bump 的 variable 有機會更早被挑出來。這讓我更理解為什麼 SAT solver 的 decision ordering 不是固定順序掃過去，而是會根據 conflict 經驗動態改變。

Learning technique 的核心在 `analyze()`。我讀這段時最有感的是 `pathC` 變數，它其實是在數目前 decision level 還有多少條 conflict path 尚未被解析完。當一路沿著 reason clause 往回解析，直到 `pathC` 歸零時，就得到 1st UIP 附近的 asserting clause。這讓我把原本抽象的 UIP cut 連回實作中的迴圈條件。

Proof database simplification 則能對到 `reduceDB()`。它不是隨便刪，而是先排序 learnt clauses，再避開 locked clause，最後依 activity 與大小做刪除。這個函式讓我看到一個很重要的實作觀念：CDCL solver 的 learned clauses 雖然都是 sound 的，但不代表全部都值得永遠留在記憶體裡。

這次我最大的收穫是，投影片上的 13 行 pseudo code 不是和原始碼分離的概念圖。MiniSat 的程式幾乎就是把那些步驟變成資料結構和函式呼叫。當我能把 `propagate()`、`analyze()`、`record()`、`reduceDB()` 對回流程圖時，SAT solver 就不再像黑盒。

### Implement at least one new SAT-related command in GV

我這次新增的 command 是：

/// collapse-code
```text
SATSolve STATs -File <dimacsFormatFileName>
```
///

我選這個功能，是因為它剛好可以把 MiniSat 內部最適合觀察的 public statistics 摘出來，而且不需要改 CDCL 搜尋核心。原本的 `SATSolve DIMACS` 會印出完整 SAT model，對小例子還可以，但如果只是想比較 solver 行為，model 會讓輸出太長。因此我新增一個只印摘要的指令，讓結果比較適合放進學習筆記。

實作上，我改了 `gv/src/sat/satCmd.h` 和 `gv/src/sat/satCmd.cpp`，新增 `SatSolveStatsCmd` 並在 `initSatCmd()` 註冊 `SATSolve STATs`。接著我在 `gv/src/sat/satMgr.h` 和 `gv/src/sat/minisatMgr.h` 加上 `solve_dimacs_stats()` 介面，最後在 `gv/src/sat/minisatMgr.cpp` 實作統計輸出。

我也順手把 DIMACS 讀取流程抽成 `load_dimacs_cnf()`，讓 `solve_dimacs_cnf()` 和 `solve_dimacs_stats()` 共用同一套 parse 和 solver construction 流程。這個 parser 後來改成 token-based，不再假設一行一定是一個 clause，而是照 DIMACS 的 `0` 結束規則累積 literals。這樣比較不會出現兩個 command 對同一個 DIMACS 檔讀法不一致的問題，也比較接近標準格式。

另一個我修掉的小坑是 `MinisatMgr` 的生命週期。原本 command 直接 `new MinisatMgr()` 後沒有釋放，因為 default constructor 和 `SolverV` destructor 不夠安全，硬補 `delete` 會 crash。我最後把 default constructor 初始化成 DIMACS 模式可安全使用的狀態，也讓 `SolverV` 的暫存 clause pointer 有明確的 null guard。這讓 command 可以用 stack object，不必靠故意 leak 來避免解構問題。

最後我新增了兩個測試 dofile：

### Then, summarize and share what you have learned.

我原本以為新增一個 SAT command 可能會需要改 solver 的核心，後來發現比較穩的做法是先找已經公開而且語意清楚的資料。`stats.conflicts`、`stats.decisions`、`stats.propagations` 和 `nLearnts()` 就很適合，因為它們本來就是 solver 對外可觀察的行為摘要。相較之下，直接拿 `trail` 或 `watches` 做輸出雖然看起來更深入，但很容易和內部 invariant 綁在一起。

這個小 command 也讓我更理解 SAT solver 實驗該看什麼。`result=SAT` 或 `result=UNSAT` 只是終點，真正有學習價值的是過程的形狀。例如 SAT case 沒有 conflict，代表很快找到一組 model；UNSAT case 則有 conflicts、learnts 和更多 propagations，代表 solver 需要透過 learning 把搜尋空間逐步堵住。

我也注意到，原本 `SATSolve DIMACS` 的 progress table 只是在 search 前印當下狀態，若直接拿那一列當最終統計，很容易誤讀。因此我保留並更新先前加的 `STATS conflicts=...` 最終輸出，讓完整 model 版和摘要版都能拿到 solve 之後的數據。

這次最大的收穫是，讀 MiniSat source code 不只是看懂一個 solver，而是學會尊重既有 abstraction。GV 的 command 層負責互動，`MinisatMgr` 負責把 GV 世界接到 solver，`SolverV` 負責 CDCL 內部狀態。我的修改只加在前兩層，沒有破壞第三層，這讓功能夠用，也比較穩。
